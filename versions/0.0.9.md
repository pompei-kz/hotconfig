# Version 0.0.9

Released: 2026-09-07

## Summary

Version 0.0.9 makes the JDBC tunnel trigger configurable and teaches it to mark the whole configuration file as changed.
In PostgreSQL a change of one parameter row now also refreshes the last modification timestamp of the configuration row - the row
where the parameter name is empty - so a parameter value edited directly in the database is seen as a change of the whole
configuration file. Trigger and trigger function names are no longer hardcoded and come from templates on the builder.

The table, the trigger and the trigger function are now checked one by one, and every one of them is created only when it is really
missing or outdated. An existing table may have no trigger, so the trigger is never taken for granted, and a database which is
already prepared needs no rights for DDL at all.

## Added

- `ConfigTunnelJdbcBuilder.triggerName(...)` / `triggerName()` for the trigger name template, defaulting to `%__trigger`. The percent
  sign (`%`) is replaced with the name of the table the trigger is attached to, without the schema part.
- `ConfigTunnelJdbcBuilder.triggerFnName(...)` / `triggerFnName()` for the trigger function name template, defaulting to
  `%__trigger_fn`. Used by PostgreSQL only - MariaDB creates the trigger without a separate function.
- `ConfigTunnelJdbc.Def.triggerName` and `ConfigTunnelJdbc.Def.triggerFnName`.
- `ConfigTunnelJdbc.triggerName()`, `triggerFnName()`, `schemaName()`, `simpleTableName()` and `withSchema(...)` as protected helpers
  for name resolution. The function name is qualified with the schema of the table when the table name has a schema part; the
  PostgreSQL trigger name is never qualified, because PostgreSQL takes the table from `CREATE TRIGGER ... ON <table>`.
- MariaDB table creation now also creates a `BEFORE UPDATE` trigger which refreshes the last modification column of the changed row.
  Before this version the MariaDB table relied on `ON UPDATE CURRENT_TIMESTAMP` only.
- `ConfigTunnelJdbc.tableExists(...)` as an abstract check of the table, implemented through `to_regclass` in PostgreSQL and through
  `information_schema.tables` in MariaDB. The table is created only when this check says the table is missing, so
  `CREATE TABLE IF NOT EXISTS` is no longer sent to an existing table.
- `ConfigTunnelJdbc.triggerExists(...)` and `ConfigTunnelJdbc.isDuplicateObject(...)`. The trigger is created only when it is missing,
  and the error of a race between two applications creating the same trigger is not a failure, because the trigger is there anyway.
- Builder validation of the trigger templates: an empty template and a template containing a period (`.`) are rejected, because the
  schema always comes from `tableName`.
- JDBC tests covering triggers:
  - the last modification timestamp of the changed row is refreshed
  - a change of a parameter row refreshes the configuration row in PostgreSQL, and provably does not in MariaDB
  - the configuration row of another configuration in the same table stays untouched
  - custom `triggerName` / `triggerFnName` templates are applied and the trigger really exists in `information_schema.triggers`
  - a schema-qualified table name works end to end (PostgreSQL only - the MariaDB test user may not create databases)
  - a table which exists without a trigger gets the trigger back, and the timestamps work again after that
  - an existing trigger stays the very same object, checked through `pg_trigger.oid` (PostgreSQL only - MariaDB shows no identity
    of a trigger)
  - a trigger left with the body of an older version is brought up to date, separately for the PostgreSQL function and for the
    MariaDB trigger body
  - empty and period-containing trigger templates make `build()` throw `IllegalArgumentException`
- Test helpers `JdbcTestDbUtils.lastModified(...)`, `triggerExists(...)`, `triggerBody(...)`, `triggerOidPg(...)`, `dropTrigger(...)`
  and `execSql(...)`.

## Changed

- PostgreSQL trigger and function names now come from the builder templates instead of the hardcoded
  `trg_<table>_last_modified` / `fn_<table>_last_modified`.
- The PostgreSQL trigger function additionally runs an `UPDATE` of the configuration row of the same configuration. The update is
  guarded by `NEW.<colParamName> <> ''`, so it never recurses further than one level, and by
  `<colLastModified> <> CURRENT_TIMESTAMP`, so it happens at most once per transaction per configuration row.
- `createTableIfNotExists()` in both dialects now asks `tableExists(...)` first and runs the schema and table DDL only when the
  table is missing. An existing table gets no DDL beyond the already existing check of the order column.
- The trigger is no longer dropped and created again on every tunnel instance. The trigger is created only when it is missing, and
  in PostgreSQL the function of an existing trigger is replaced only when its body differs from the body of this version - the body
  is compared with `pg_proc.prosrc`, and in MariaDB with `information_schema.triggers.action_statement`. A database which is already
  prepared gets no DDL at all, and an existing trigger is never dropped, so there is no moment when changes of the table are not
  caught by anybody.
- `ConfigTunnelJdbc.createSchemaIfNotExists(...)` and the internal `columnExists(...)` now split the schema and the table through
  `schemaName()` / `simpleTableName()` instead of parsing the period separately in each method.
- README documents the trigger, the name templates and the MariaDB limitation.

## Migration Notes

- The database user needs the rights to create triggers, and in PostgreSQL to create functions, only until the trigger is created.
  After that no DDL is run, and rights to read and write the data of the table are enough. A user with such reduced rights cannot
  even send `CREATE TABLE IF NOT EXISTS` for an already existing table - in PostgreSQL it fails with
  `permission denied for schema public` - and this is why the table is checked before any DDL.
- Changing `triggerFnName` on a table which already has a trigger leaves the trigger pointing at the old function. Drop the trigger
  once after such a change, so it is created again with the new function name.
- The trigger of version 0.0.8 is not removed automatically, because its name does not match the new template. In PostgreSQL both
  triggers keep working - the old one only refreshes the changed row, so the result stays correct, but the old pair is dead weight.
  Drop it manually:

  ```sql
  DROP TRIGGER IF EXISTS trg_hotconfig_last_modified ON hotconfig;
  DROP FUNCTION IF EXISTS fn_hotconfig_last_modified();
  ```

  In the names above `hotconfig` is the table name with every run of non-alphanumeric characters replaced with `_`, which is how
  version 0.0.8 built these names.

- MariaDB forbids a trigger to change the table it is attached to (error 1442: `Can't update table ... in stored function/trigger
  because it is already used by statement which invoked this stored function/trigger`), and the error would appear on every `UPDATE`
  of the table, not at trigger creation. Because of this the MariaDB trigger refreshes the changed row only. There the change of the
  whole configuration is still seen, because `modificationMarker` reads `MAX(<colLastModified>)` over all rows of the configuration.

- To use different names, configure the templates on the builder:

  ```java
  ConfigTunnelJdbc tunnel = ConfigTunnelJdbc.builder()
    .connectionGet(() -> dataSource.getConnection())
    .tableName("hotconfig")
    .triggerName("%__trigger")
    .triggerFnName("%__trigger_fn")
    .build();
  ```

- Triggers are created inside `createTableIfNotExists()`, which runs once per tunnel instance. A trigger dropped externally is not
  recreated until a new tunnel instance is built.
