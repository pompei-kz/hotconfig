# Version 0.0.12

Released: 2026-09-29

## Summary

Version 0.0.12 fixes the starving of a rarely read configuration by the revision checks of the others.

A value of a configuration is cached, and the storage is asked whether it has changed no more often than
`revisionCheckTimeoutMs` (two seconds by default). The moment of the last check was one for the whole factory: whichever
configuration was read first after the timeout made the check, and every other configuration read within the next timeout
returned its cached value without looking at the storage at all.

In an application which reads some configuration on every request - a servlet filter, a long-polling loop, a heartbeat -
that configuration takes the check for itself again and again, and a configuration which is read rarely, say once when a
page opens, gets its check only when its read happens to fall into the gap between the end of the timeout and the next
frequent read. Under a steady stream of requests this may never happen: the value edited in the database is not seen until
the application is restarted, although the library is there exactly to make a restart unnecessary.

Now every configuration keeps the moment of its own last check. A read which comes more than the timeout after the last
check of **that** configuration always asks the storage, no matter what the other configurations did in the meantime; a read
which comes sooner is still served from the cache, so the storage is asked no more often than before for each configuration.

## Fixed

- `HotConfigFactory.getDot(...)`: the revision check of one configuration no longer postpones the check of another one.

## Added

- `HotConfigFactoryTest.getDot__revisionCheckOfOneConfDoesNotPostponeCheckOfAnother`: TestConf2 is read right after the
  timeout and takes its check; TestConf1, changed in the storage in the meantime, is read a little later and must see its
  change; right after its own check it is throttled again.

## Migration Notes

- Nothing has to be done: no change of the API, of the database or of the storage.
- The storage may be asked a little more often than before: once per configuration per timeout instead of once per factory
  per timeout. The check is one light query (`SELECT MAX(last_modified_at) ...` in the JDBC tunnel) and only for the
  configurations which are actually read.
