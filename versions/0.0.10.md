# Version 0.0.10

Released: 2026-09-08

## Summary

Version 0.0.10 brings the timestamps of the PostgreSQL configuration table to `TIMESTAMPTZ` - `timestamp with time zone`.

Before this version `colCreatedAt` and `colLastModified` were of the plain `TIMESTAMP` type - a wall clock without any time zone.
Such a value says nothing about the moment it means: the very same text is read as another moment by an application whose time zone
differs from the one which wrote it, so the comparison of the last modification timestamp with the clock of the application started
to lie as soon as the application and the database did not agree on the time zone. `TIMESTAMPTZ` keeps the moment itself, and every
reader sees the very same moment.

A table made by an older version of this library is brought to the new type automatically: the type of both columns is checked every
time the table is checked - just as the column of the row order and the trigger are - and a column which keeps a timestamp without a
time zone is changed to `TIMESTAMPTZ`. The values of the rows survive the change: PostgreSQL reads the old wall clock in the time zone
of the session, which is exactly how the old value was written and how this library used to read it back.

MariaDB keeps the path it had before. Its own `TIMESTAMP` is stored in UTC and shown in the time zone of the session, so it already
keeps the moment itself; the type without a time zone in MariaDB is `DATETIME`, and this library has never used it.

## Added

- `ALTER COLUMN ... TYPE TIMESTAMPTZ` for a PostgreSQL table whose timestamp columns have no time zone. The change runs inside
  `createTableIfNotExists()`, next to the check of the order column and the check of the trigger, so it is done for a table which
  comes from an older version of this library or was made by hand.
- The check of the type of a column through `information_schema.columns.data_type`. Only a column of the type
  `timestamp without time zone` is changed - a column of any other type is left alone, because the owner of a hand-made table knows
  better what belongs there. Nothing is changed when both columns already keep the time zone, so a database which is already prepared
  needs no rights for DDL at all.
- The race of several instances which start at the same moment is handled here as it is handled everywhere else: the loser of the
  race for `ALTER COLUMN` swallows its error only when the column is of the wanted type anyway.
- JDBC tests:
  - a fresh PostgreSQL table keeps both timestamp columns as `timestamp with time zone`
  - a table whose columns were brought back to the plain `TIMESTAMP` - the table of an older version - gets `TIMESTAMPTZ` when the
    mechanism runs, and the values of the row stay where they were: the same wall clock in the same time zone, and the same moment as
    read by `modificationMarker`. A second run of the mechanism has nothing left to do and breaks nothing
  - the same change for a schema-qualified table name
  - eight instances start at the same moment and race for `ALTER COLUMN ... TYPE TIMESTAMPTZ`, and nobody falls
- Test helpers `JdbcTestDbUtils.columnDataType(...)` - the type of a column as the database itself names it - and
  `timestampAsText(...)` - the value of a timestamp as the wall clock which the database shows in the time zone of the session, so the
  very same text before and after the change of the type means the moment of the row has not moved anywhere.

## Changed

- The PostgreSQL `CREATE TABLE` now creates `colCreatedAt` and `colLastModified` as `TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP`
  instead of `TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP`.

## Migration Notes

- Nothing has to be done by hand: the type of the columns is checked and changed when the table is checked - that is, once per tunnel
  instance, inside `createTableIfNotExists()`.
- The database user needs the right to `ALTER` the table only until the columns are changed. After that the check finds both columns
  with the time zone and runs no DDL at all, so rights to read and write the data of the table are enough again. When such a right
  cannot be given, the change can be made by hand once:

  ```sql
  ALTER TABLE hotconfig ALTER COLUMN created_at       TYPE TIMESTAMPTZ;
  ALTER TABLE hotconfig ALTER COLUMN last_modified_at TYPE TIMESTAMPTZ;
  ```

- `ALTER COLUMN ... TYPE` rewrites the table and holds an `ACCESS EXCLUSIVE` lock on it while it runs. The configuration table is
  small, so this is a matter of milliseconds, but it happens on the first start of an application of this version.
- The old wall clock is read in the time zone of the session which runs the change. The PostgreSQL JDBC driver sets this time zone
  from the time zone of the JVM, which is the very time zone in which the old values were written and read back by the previous
  versions of this library, so the moment of every row stays the same. If the timestamps of the table were written by something else,
  in another time zone, check that the values mean what they should after the change.
- The default of the column is not touched: PostgreSQL brings the default expression to the new type by itself, so
  `CURRENT_TIMESTAMP` stays `CURRENT_TIMESTAMP`, and a column made by hand keeps the default it was given.
- MariaDB is untouched by this version.
