# Version 0.0.11

Released: 2026-09-15

## Summary

Version 0.0.11 fixes a race of the very first write of a configuration, and makes the value which is already in the database the
value that counts.

Two instances of an application which start at the same moment on a new database ask the same configuration for the first time.
A value which is not in the table yet is written back with its default, so both of them write the same configuration into the
same empty table. The check "is the row there" and the insert of the row cannot be made one atomic step, so the loser of this
race got a violation of the primary key:

```
E1f2G3h4I5 :: Could not write configuration to table: conf.hot_config
Caused by: org.postgresql.util.PSQLException: ERROR: duplicate key value violates unique constraint "hot_config_pkey"
  Detail: Key (folder, class_name, name)=(map, MapServiceConf.hotconf, ) already exists.
```

The row of the config was written by the instance which won, so the data was never lost - but the task of the loser died on the
way, wherever it was. This is a race of a first start only: on the second start the rows are already there, and nothing is
written at all, which is why it shows itself on a new database and nowhere else.

Now `write(...)` only brings the rows which are not in the table yet, and never takes away or changes a row which is already
there. A row that is there wins over everything written after it, and the instance which came first is the one whose value
stays. Nobody waits for anybody and nothing is deleted, so there is no window in which a configuration is half-written.

## Changed

- `ConfigTunnel.write(...)` of the JDBC tunnel no longer deletes the rows of the configuration before writing it. The statement
  which removed them was the reason two instances writing at the same moment could leave a configuration mixed of both - the
  comment of one instance next to the parameter value of another one - or even leave the table empty, when the last delete came
  after all the inserts.
- The insert of a row carries `ON CONFLICT DO NOTHING` in PostgreSQL and a no-op `ON DUPLICATE KEY UPDATE` in MariaDB, so a row
  which is already there is left exactly as it is.
- Taken together, this is the rule of the whole tunnel now: **the value in the database is the value that counts**. Code brings
  the values which the database does not have yet; it never argues with the ones it has.

## Fixed

- `ConfigTunnelJdbc.write(...)` no longer fails with a violation of the primary key when two instances write the same
  configuration at the same moment.
- `ConfigTunnelJdbc.writeNoticeLines(...)` had the same race - the row of the whole config is not there yet, so every instance
  sees nothing to update and goes on to insert the row. The loser now writes its notice into the row which the winner has just
  made, so the notice is never lost.

## Added

- `ConfigTunnelJdbc.onConflictDoNothing()` as the dialect-specific tail of the `INSERT`.
- JDBC tests: eight instances writing the same configuration into an empty table at once; the same over rows which are already
  there, where nothing may change; eight instances writing **different** values of the same parameter at once, where the table
  must keep one of them whole; the same race for the notice of a configuration; and a check of the statement itself.

## Migration Notes

- Nothing has to be done with the database: no change of the table, of its columns or of its trigger.
- **`write(...)` no longer changes anything that is already in the table.** A parameter which is not there yet is added, and this
  is what the library needs it for - a new parameter of a configuration gets its default into the database. Everything else
  stays as the database has it:
  - a value edited in the database is never overwritten by the default from the code - which is the point of this version;
  - a comment changed in the code does not reach a row which is already there;
  - an error found in a value is not written into the row of that value, so the column of the error stays as it was for a
    configuration which is already in the table;
  - a parameter removed from the code leaves its row in the table forever - `write(...)` deletes nothing.
- A row which is already there is left as it is, and is not brought to the values of the instance which came second. Refreshing
  it would mean an `UPDATE`, and an `UPDATE` wakes the trigger of the table, which in PostgreSQL updates a second row - the row
  of the whole config - inside the very same statement.
- The library still never opens a transaction of its own: the connection belongs to the application, which may well be inside a
  transaction already. It needs none here - every row is written by one statement which either brings the row or leaves it.
